# ADR-0001：文档事实分层与需求追踪

- 状态：已接受
- 日期：2026-09-18
- 决策者：项目维护团队
- 关联：文档架构治理

## 背景

原文档集合已覆盖需求、架构、API、测试和模板，但需求位于计划目录，进度文档同时包含事实、差距和 backlog，部分链接指向不存在的短期计划/事实快照。相同状态在多处复制会随开发快速漂移。

## 决策驱动因素

- 新开发者能在数分钟内找到当前事实和工作入口。
- 产品目标不能被误解为已交付能力。
- 每项需求可追溯到实现模块、测试和发布证据。
- 文档维护成本随模块数量增长时仍可控。

## 备选方案

1. 保留现状，仅扩充总索引：迁移成本低，但不解决职责混杂和事实重复。
2. 按读者任务分层并建立追踪矩阵：需要维护链接，但事实边界清晰。
3. 立即引入完整文档站和数据库：检索体验好，但当前规模下工具和维护成本过高。

## 决策

采用方案 2。建立 `requirements`、`guides`、`decisions`、`operations` 四类缺失文档；保留既有 API、架构、质量、诊断、计划和模板目录。代码/构建为可执行事实真源，ADR 保存关键选择，追踪矩阵保存需求到证据的链接，进度文档保存状态。

## 后果

### 正面

- 需求、状态、计划、设计和操作说明有明确边界。
- MR 可使用稳定需求 ID，并以测试作为状态证据。
- 关键决策不再埋在长篇架构或进度文档中。

### 负面与风险

- 旧链接需要迁移，矩阵需要每迭代核验。
- 既有长文档仍需按模块逐步去重，不能一次性自动判定语义重复。

## 验证与复审

- CI/本地文档检查不得出现失效相对链接。
- 每个里程碑抽查至少一个需求的端到端追踪链。
- 当文档数量或外部用户显著增长时，复审是否引入静态文档站与 API 自动生成。
