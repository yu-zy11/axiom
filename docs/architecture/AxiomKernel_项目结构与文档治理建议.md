# AxiomKernel 项目结构与文档治理规范

> 状态：已接受
> 责任域：Project
> 维护者：项目负责人
> 最后核验：2026-09-18
> 核验依据：仓库目录、`CMakeLists.txt`、`cmake/AxiomKernelLibraries.cmake`

## 1. 目的

本规范定义代码与文档如何共同成为可维护的工程系统。它替代一次性的“治理建议”：后续评审应直接据此判断文档位置、事实归属、更新责任和完成标准。

## 2. 代码结构边界

| 路径 | 职责 | 约束 |
|---|---|---|
| `include/axiom/` | Public API | 可安装、保持兼容；不得暴露 internal 类型 |
| `src/axiom/<module>/` | 模块实现 | 与公开模块对应，跨模块依赖由 CMake target 表达 |
| `src/axiom/internal/` | 私有实现契约 | 不安装；插件及上层不得引用 |
| `tests/<module>/` | 自动化证据 | 测试名称由根 `CMakeLists.txt` 注册 |
| `examples/` | 可编译的主链路样例 | API 变化时与头文件同步 |
| `cmake/` | target 与依赖真源 | 不在文档中另造不同依赖图 |
| `docs/` | 需求、设计、使用与交付知识 | 按 §3 分类，不承载代码真源 |

模块边界和允许依赖详见[模块依赖图](AxiomKernel_模块依赖图与时序图.md)。新增跨模块依赖必须更新 CMake、架构说明，并在不可轻易逆转时提交 ADR。

## 3. 文档分类规则

文档必须按主要读者问题归档：

- `requirements/`：产品目标、范围、可验收需求与追踪矩阵。
- `plan/`：路线图、当前状态、近期 backlog、历史纪要。计划不是规范。
- `architecture/`：系统结构、边界、时序和长期设计约束。
- `decisions/`：重要决策的上下文、选项、结论与后果。
- `api/`：公开契约说明和集成样例；头文件优先。
- `guides/`：面向贡献者的任务型操作指南。
- `quality/`：测试层级、数据集、性能和验收门禁。
- `diagnostics/`：稳定错误码、诊断语义和用户文案。
- `operations/`：版本、制品、发布验证、回滚与事故操作。
- `templates/`：重复流程的可复制模板。

一个文档若跨多个分类，应选择其主要职责，其余章节链接到对应真源。禁止复制完整 API、测试清单或 backlog 来“保持方便”。

## 4. 文档生命周期

1. **草案**：作者明确问题、读者、范围和依据，可在 MR 中迭代。
2. **评审中**：涉及的模块负责人确认事实、术语、风险和可执行性。
3. **已接受**：成为执行依据；后续改变通过普通 MR 或 ADR 完成。
4. **已废弃**：正文顶部给出替代文档和废弃原因；不静默删除仍被外部引用的契约。

所有新文档至少包含状态、责任域、维护者、最后核验日期、核验依据。进度快照每个迭代核验；API、诊断和运维文档随代码触发核验；长期概念文档至少每个里程碑核验。

## 5. 需求到交付闭环

每项可交付能力必须形成以下链路：

`需求 ID → 负责模块 → 路线图阶段/backlog → Public API 或内部设计 → 自动化测试 → 诊断/可观测证据 → 发布说明`

[需求追踪矩阵](../requirements/AxiomKernel_需求追踪矩阵.md)负责保存链接，不复制实现细节。状态定义统一如下：

- **未开始**：没有可运行实现。
- **进行中**：存在实现或测试，但未满足需求验收标准。
- **受限可用**：在公开声明的输入域内满足验收，限制有测试和诊断。
- **已满足**：完整满足需求定义及门禁。
- **阻塞**：有明确外部决策或依赖，必须记录解除条件。

“有接口”“有示例”或“测试通过”单独均不等于“已满足”。成熟度声明以需求中的证据要求和当前进度为准。

## 6. 变更完成定义（DoD）

每个 MR 必须回答：

- 需求：关联哪个需求 ID / 缺陷？验收标准是什么？
- 架构：模块归属和依赖方向是否正确？是否需要 ADR？
- 接口：Public API、兼容性和样例是否同步？
- 失败：是否使用稳定错误码，重量级路径是否可追踪？
- 一致性：失败、取消或异常是否污染模型？
- 证据：单元/组件/集成/回归测试覆盖了哪些成功与失败路径？
- 性能：是否触碰热路径，基线如何比较？
- 文档：追踪矩阵、状态、诊断、发布说明中哪些需要更新？

未涉及的项目应明确写“不涉及”并给出原因，而不是留空。

## 7. 文档质量门禁

- 所有仓库内相对链接必须可解析，锚点尽量使用稳定标题。
- 示例代码若声称可运行，应由 `examples/` 或测试承载；文档只引用它。
- 不记录个人机器绝对路径、临时结论或无责任人的 TODO。
- 使用绝对日期；时间估算必须标注假设，不与阶段状态混用。
- 图表使用可审查的文本格式（优先 Mermaid），并附文字说明。
- 删除或移动文档前，先更新所有仓库内引用；外部契约需要保留迁移提示。

## 8. 定期维护节奏

| 时点 | 必做动作 |
|---|---|
| 每个 MR | 运行链接检查；按影响速查更新文档 |
| 每个迭代 | 清理 backlog；核验当前进度和追踪矩阵 |
| 每个里程碑 | 复核需求范围、架构、质量门禁和风险；关闭或替代过期 ADR |
| 每次发布 | 按发布手册记录版本、制品、测试、兼容性与回滚点 |
