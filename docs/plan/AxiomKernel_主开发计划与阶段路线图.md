# AxiomKernel 主开发计划与阶段路线图

本文档定义 `AxiomKernel` 从**当前已达成 Stage 1、Stage 2 可测基线（见《当前开发进度》§1 / §5.2 归档）**的起始状态，到“工业级完整几何引擎阶段”的总路线、阶段目标、关键里程碑、退出标准和长期演进方向。该文档作为整个项目的主计划文档，后续开发、测试、文档、发布都应以本计划为总参照；**当前构建/测试事实**以 [AxiomKernel_当前状态事实快照.md](AxiomKernel_当前状态事实快照.md) 为准，**滚动进度与 backlog** 以《当前开发进度》为准；**近期选取顺序**见[短期执行计划](AxiomKernel_短期执行计划.md)，任务状态仍在进度 **§5.2.1**。文档导航见 `docs/README.md`；结构与文档治理问题见 `docs/architecture/AxiomKernel_项目结构与文档治理建议.md`；批次历史见 `docs/plan/AxiomKernel_变更纪要.md`。

## 1. 当前阶段判断

截至当前，项目已完成：

- 文档体系初步成型
- 模块划分、接口边界、错误码、测试策略已定义
- **Stage 0**：基础代码框架、`Kernel` 门面与主要服务骨架、示例与 smoke 测试
- **Stage 1**：全量工程可编译；`Result`/诊断/错误码接入主链路；多模块专项 `ctest` 与 IO/布尔/表示等工作流回归形成门禁

当前阶段可定义为：

`Stage 1 已达成；Stage 2 可测基线已达成；当前为 Stage 2 深化与 Stage 3 准备：基础建模与查询分析为主线`

**说明**：原 **Stage 1.5 / Stage 2 过渡** 所承载的 backlog 批次已在《当前开发进度》**§5.2 归档表**全部闭合；**不等于**工业级引擎完成（工业布尔等见 Stage 4 与进度文档 §3.4）。**进行中 backlog** 以《当前开发进度》**§5.2.1** 为唯一入口。这里描述的是**阶段定位**，不是“当前分支此刻全量测试已绿”的声明。

**本阶段退出标准（与代码、测试对齐的最低门禁，仍须持续满足）**：

- 根目录 `cmake` 配置与完整构建通过，全量 `ctest` 绿
- `Kernel::io_can_import_format` / `io_can_export_format` 与 `IOService::import_auto` / `export_auto` / `detect_format` 的格式集合**一致**（或由 API 文档明确双口径并有回归断言）
- 高风险链路（BOOL/HEAL/IO）关键诊断可在 `DiagnosticService` 检索，且 JSON 导出可携带工作流阶段字段（`Issue.stage`）以便 CI 归档

## 2. 最终目标定义

最终目标不是“做一个能演示的 CAD 内核”，而是构建一个在以下维度上全面领先传统闭源内核和开源内核组合方案的新一代几何引擎：

- 更强的鲁棒性
- 更现代的架构分层
- 更强的可诊断性
- 更好的缓存与增量重算能力
- 更好的混合表示支持
- 更好的插件化和云端扩展能力
- 更一致的 API 与工程化能力

## 3. 与现有内核竞争的核心能力目标

相对 `CATIA/CGM`、`SOLIDWORKS/Parasolid`、`ACIS`、`OCCT`，最终要追求的核心差异：

### 3.1 比传统商业内核更强的点

- 更细粒度的诊断和错误证据
- 更清晰的几何/拓扑/修复/缓存分层
- 更好的增量更新架构
- 更自然的混合表示支持
- 更好的插件和远程服务化能力

### 3.2 比开源内核更强的点

- 更强的布尔鲁棒性
- 更强的复杂圆角/抽壳能力
- 更成熟的工程流程和测试体系
- 更稳定的 API 和错误码体系

## 4. 总体开发阶段

建议把完整项目分成 9 个大阶段。

## 4.1 `Stage 0` 文档与骨架

状态：

- 已完成

目标：

- 架构清晰
- 工程可编译
- 目录和文档体系建立

## 4.2 `Stage 1` 编译基线与核心公共层稳定

目标：

- 当前骨架全部编译通过
- 结果对象、错误码、诊断对象、基础类型稳定
- 基本构建、测试、示例可运行

退出标准：

- `cmake` 可构建
- smoke test 通过
- 示例程序可运行

## 4.3 `Stage 2` 基础几何与拓扑内核落地

**与当前仓库对齐**：本阶段目标涵盖原「`Stage 1.5 / Stage 2` 过渡」中**收束几何/拓扑过渡实现与回退路径、容差与 trim 契约、Strict 与诊断可测性**的可测部分（已在《当前开发进度》**§5.2 归档**闭合基线）；**持续深化**（全规则集、工业 trim 等）仍在 Stage 2 内进行。当前实时事实见 [AxiomKernel_当前状态事实快照.md](AxiomKernel_当前状态事实快照.md)，证据索引与归档见《当前开发进度》。

**详细待拍板项（推荐默认、备选、DoD、ctest）**：[AxiomKernel_待拍板与架构决策清单.md](AxiomKernel_待拍板与架构决策清单.md)。

### 目标

- **Math**：容差策略可文档化、可测试；近退化谓词行为有统一约定（见 DEC-MATH-*）。
- **Geo**：解析与样条主链路的 eval/domain/bbox/closest 语义稳定；`Trimmed` 的 **subset 语义**对外写清，并向 UV loop + PCurve 路线过渡（见 DEC-GEO-*）。
- **Topo**：Strict 规则集 **v1** 可列举（定向、开放边界、非流形、trim bridge 验收）；事务 **MVP 单写** 语义入文档（见 DEC-TOPO-*）。
- **Diag**：BOOL/HEAL/IO 关键失败路径保持可检索与 `Issue.stage`；阶段化 checklist 启动（见 DEC-DIAG-*）。
- **Rep / IO / Eval / Plugin**：不强制在本阶段闭环工业化，但须在清单中 **已提议、暂缓或 Stage 8 已立项** 明确，避免静默扩张范围。（**Plugin Stage 8 安全轨道**见 **DEC-PLUGIN-001** / 进度文档 **§5.6.11**，**非**本阶段退出门禁。）

### 退出标准（可测最低门禁）

- 根目录 `cmake` 配置与完整构建通过，全量 `ctest` 绿。
- **容差与数学**：`axiom_math_services_test` 覆盖 DEC-MATH 已采纳条目中要求的用例（含非法输入/退化路径）；容差优先级行为有文档短表（可放在清单或 `docs/api`）。
- **几何与拓扑**：`axiom_geometry_test`、`axiom_topology_test` 对 Stage 2 已采纳的定向、trim bridge、Strict 失败类有 **新增或既有** 回归断言（与清单 DoD 对齐）。
- **诊断**：高风险链路（BOOL/HEAL/IO）失败仍可通过 `DiagnosticService` 检索；JSON 导出携带 `Issue.stage`（与 Stage 1 门禁一致并持续不回归）。
- **门面 IO 能力**：`Kernel::io_can_import_format` / `io_can_export_format` 与 `IOService::detect_format` / `import_auto` / `export_auto` 一致，或由 API 文档明确双口径并有 `axiom_smoke_test` 断言。

### 本阶段非目标（明确不承诺）

- **工业级布尔闭环**（完整分类/重建/大规模数据集）：留给 Stage 4 及 DEC-OPS-* 迭代。
- **进程外插件隔离、动态库安全加载与供应链治理**：**Stage 8 正式立项**（**DEC-PLUGIN-001** **已评审-采纳**，交付切片见进度文档 **§5.6.11**）；**仍非** Stage 2～7 的退出门禁。
- **Eval 硬指标 CI 门禁**（命中率/图规模阈值）：默认暂缓，见 DEC-EVAL-002。
- **标准 IGES 实体级与通用 3MF 全量读写**：按 DEC-IO-001 排期，本阶段不强制交付。

## 4.4 `Stage 3` 基础建模与查询分析

**与当前仓库对齐**：本阶段并非从零开始。当前代码已具备若干可回归的 Stage 3 子路径，包括 polygon `extrude`、子午面 polygon `revolve`、line-segment / polyline 子集 `sweep`、polygon `loft`、planar / subset 非平面 `thicken`、单面 `draft`、sphere-plane `section`、sphere-sphere / sphere-box 最近距离，以及部分 polyhedral / 解析体 `mass_properties`。但这些仍以“可证明子集 + 前置拒绝 + 回滚不污染”为主，尚未形成可对外宣称的 Stage 3 主链闭环。

目标：

- 基础体构造
- 拉伸、旋转、扫描基础能力
- 截面、最近点、体积、面积、重心等查询稳定

退出标准：

- 基础零件建模闭环跑通
- 质量属性结果正确
- `extrude/revolve/sweep/loft/thicken` 至少各有一条**非占位、非 bbox 近似**的主路径，并以 `ctest` 回归锁定支持边界
- `section`、最近点/最近距离、`mass_properties` 在 Stage 3 已声明支持的体类上保持一致语义，失败路径具备稳定 `Issue.stage`
- topology / rep / provenance / eval 对 Stage 3 主链结果保持一致，不因失败回滚或 fallback 漂移

**进入本阶段前仍需收口的事项**：

- 把当前分散在 `ops_heal`、`query_eval`、`representation_io`、`geometry` 中的 Stage 3 frontier 证据整理为统一支持矩阵
- 收敛查询分析的 fallback 语义，避免 `section_bbox_plane`、局部解析截面与质量属性恢复在不同体类上口径不一
- 对已声明支持的建模路径补齐跨模块一致性断言，而不只验证单点成功
- 维持全量 `ctest` 绿并继续压缩 `AXM_ENABLE_STRICT_WARNINGS=ON` 下的历史告警

## 4.9 `Stage 8` 混合表示与插件生态

## 6. 每一阶段的执行方式

1. 选择一个用户工作流，冻结输入、输出、支持边界和正确性参考。
2. 将需求拆成有依赖的最小任务；实现、诊断、回滚与回归在同一切片完成。
3. 局部修改运行受影响测试；集成与阶段验收运行完整门禁，记录源码和配置。
4. 按支持矩阵与阶段退出标准判定完成；不以新增接口或失败诊断数量计完成度。

长期“优于现有内核”是产品愿景。在固定数据集、容差、硬件、版本和比较方法形成实测报告前，不作为当前能力声明或迭代验收条件。

## 7. 当前立即执行顺序

以[短期执行计划](AxiomKernel_短期执行计划.md)为选取顺序真源：实际回归阻断优先；其次 S3-01 支持矩阵、S3-02 建模跨模块闭环、S3-03 查询语义、S3-04 阶段验收。任务状态只在进度 §5.2.1 维护。

不重复立项已经完成的骨架、公共存储和基础诊断建设。Geo/Topo/Math/Heal 本轮优先服务上述链路的明确缺口；工业布尔仍是 Stage 4，标准交换是 Stage 5。专题计划中的优先级是专题内部顺序。

阶段可以有提前实现的子路径；开始阶段工作不等于宣布该阶段完成。只有对应退出标准逐条具有证据，才提升完成状态。

## 8. 完成判定

“完成本几何引擎开发”不是单一节点，而应满足以下综合标准：

- 文档体系完整
- API 稳定
- 基础几何与拓扑稳定
- 工业级基础建模稳定
- 布尔、修复、导入导出主链路稳定
- 高级特征达到可用水平
- 性能和鲁棒性达到长期目标
- 测试、CI、发布和生态能力完整

## 9. 当前策略

从现在开始，按这个主计划持续推进时，优先级固定为：

1. 保证工程始终可构建
2. 保证文档与代码一致
3. 保证每一轮新增能力都有测试和诊断
4. 先把通用底座做稳，再做工业高级特征

## 10. 结论

这个项目如果要真正达到超越传统内核的目标，本质上是一个长期系统工程，而不是单一算法工程。当前最正确的路线不是直接堆功能，而是：

- 先稳住架构
- 再稳住基线
- 再推进核心建模能力
- 再逐步进入工业难点

从下一步开始，执行重点将保持在：

`Stage 2 深化（Geo/Topo/Math/Diag）+ Stage 3 主攻（基础建模与查询分析），工业布尔闭环仍按 Stage 4 排期`

（**历史**：曾表述为 `Stage 1.5 / Stage 2 过渡`，该过渡 backlog 已全闭合，见《当前开发进度》§5.2。）
